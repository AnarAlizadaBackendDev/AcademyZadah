> **Goal:** understand how Spring Security works internally: the filter chain.
> **Duration:** 120 min

## 1. Adding Spring Security

```groovy
implementation 'org.springframework.boot:spring-boot-starter-security'
```
Restart the app: **every endpoint now requires login**; a random password is printed in the log (user `user`). Secure by default.

## 2. The filter chain

```
HTTP request
   │
   ▼
Servlet filters ─▶ DelegatingFilterProxy ─▶ FilterChainProxy ─▶ SecurityFilterChain
                                                                  ├─ CorsFilter
                                                                  ├─ CsrfFilter
                                                                  ├─ LogoutFilter
                                                                  ├─ UsernamePasswordAuthenticationFilter / BearerTokenAuthenticationFilter
                                                                  ├─ ExceptionTranslationFilter
                                                                  └─ AuthorizationFilter
   ▼
DispatcherServlet ─▶ your @RestController
```
Each filter does one job; the chain can stop a request (401/403) before it reaches your controller.

## 3. Core objects

| Object | Role |
|---|---|
| `Authentication` | who: principal + credentials + authorities |
| `SecurityContext` / `SecurityContextHolder` | stores the current `Authentication` (per thread) |
| `AuthenticationManager` / `AuthenticationProvider` | verify credentials |
| `UserDetailsService` | loads a user by username |
| `PasswordEncoder` | hashes/verifies passwords |
| `GrantedAuthority` | permission/role (`ROLE_ADMIN`) |

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
String username = auth.getName();
```

## 4. Configuration (Spring Security 6+)

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                         // stateless JSON API (see lesson 7)
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health", "/swagger-ui/**", "/v3/api-docs/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/v1/products/**").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();   // {bcrypt}... upgradeable
    }
}
```
Order matters: first matching rule wins; put specific rules first, `anyRequest()` last.

## 5. Debugging security

```yaml
logging.level.org.springframework.security: trace
```
The log shows each filter and why a request was rejected. Also `@EnableWebSecurity(debug = true)` (dev only).

## 6. Multiple chains

```java
@Bean @Order(1)
SecurityFilterChain actuator(HttpSecurity http) throws Exception {
    http.securityMatcher("/actuator/**")
        .authorizeHttpRequests(a -> a.requestMatchers("/actuator/health/**").permitAll().anyRequest().hasRole("OPS"))
        .httpBasic(Customizer.withDefaults());
    return http.build();
}
```

## 7. Hands-on

1. Add Spring Security to the shop; observe default behaviour.
2. Write `SecurityConfig` with public catalog, protected orders, admin endpoints.
3. Enable TRACE logs; follow one rejected and one accepted request through the chain.
4. Write a custom filter that adds a security header and log where it runs in the chain.

## 8. Interview corner

- How does Spring Security process a request?
- What is the SecurityContextHolder? Is it thread-safe?
- Why does the order of `requestMatchers` matter?
