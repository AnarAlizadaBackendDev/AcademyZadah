> **Goal:** learn security fundamentals every backend developer must know.
> **Duration:** 120 min

## 1. Authentication vs authorization

| | Question | Example |
|---|---|---|
| **Authentication** (AuthN) | *Who are you?* | login with password, OTP, token |
| **Authorization** (AuthZ) | *What are you allowed to do?* | only admins delete products; customers see only their orders |

401 = not authenticated; 403 = authenticated but not authorized.

## 2. CIA triad

- **Confidentiality**: only allowed people see data.
- **Integrity**: data isn't modified illegally.
- **Availability**: the system stays up.

## 3. Hashing vs encryption vs encoding

| | Reversible | Use |
|---|---|---|
| Encoding (Base64) | yes, no key | transport format: **not security** |
| Encryption (AES, RSA) | yes, with key | data you need back (card tokens, PII at rest) |
| Hashing (SHA-256) | no | integrity checks |
| Password hashing (**BCrypt**, Argon2) | no, **slow + salted** | storing passwords |

Never store passwords in plain text or with fast hashes (MD5/SHA-1/SHA-256): GPUs crack billions per second.

## 4. OWASP Top 10 (2021): what to remember

| # | Risk | Backend example | Prevention |
|---|---|---|---|
| A01 | Broken access control | `/api/orders/1025` returns another customer's order (IDOR) | check ownership on every request |
| A02 | Cryptographic failures | HTTP instead of HTTPS, MD5 passwords | TLS everywhere, BCrypt |
| A03 | Injection | SQL built with string concatenation | prepared statements / JPA params |
| A04 | Insecure design | no rate limit on OTP | threat modeling, limits |
| A05 | Security misconfiguration | Actuator `/env` public, default passwords | hardening, least privilege |
| A06 | Vulnerable components | old library with known CVE | dependency scanning (Dependabot, OWASP dependency-check) |
| A07 | Identification & auth failures | no lockout, weak passwords, long-lived tokens | lockout, MFA, short tokens |
| A08 | Software & data integrity failures | unsigned webhooks, untrusted deserialization | verify signatures |
| A09 | Logging & monitoring failures | no audit of logins/transfers | audit logs, alerts |
| A10 | SSRF | server fetches any URL a user provides | allow-lists |

## 5. IDOR: the most common API bug

```java
// ❌ anyone logged in can read any order by changing the id
@GetMapping("/api/orders/{id}")
OrderResponse get(@PathVariable Long id) { return orders.get(id); }

// ✅ check ownership
@GetMapping("/api/orders/{id}")
OrderResponse get(@PathVariable Long id, @AuthenticationPrincipal UserPrincipal me) {
    return orders.getForCustomer(id, me.customerId());   // 404 if not theirs
}
```

## 6. Threat modeling in 15 minutes (STRIDE-lite)

For each endpoint ask:
1. Who can call it? (anonymous, customer, admin, partner)
2. What can go wrong? (spoofing, tampering, data leak, abuse/DoS)
3. What's the impact? (money, personal data)
4. What control prevents it? (auth, ownership check, validation, rate limit, audit)

## 7. Hands-on

1. Review your shop API: for every endpoint, fill a table: actor, risk, control.
2. Find at least 3 IDOR/broken access control risks in your current code.
3. Compare storing a password with SHA-256 vs BCrypt (time per hash).

```java
var encoder = new BCryptPasswordEncoder(12);
String hash = encoder.encode("Secret123");     // $2a$12$...
encoder.matches("Secret123", hash);            // true
```
