> **Goal:** learn system design fundamentals and practice classic interview problems.
> **Duration:** 120 min

## 1. Approach to a system design question

1. **Clarify requirements**: functional (what) and non-functional (scale, latency, availability, consistency).
2. **Estimate**: users, requests/sec, data size.
3. **High-level design**: clients, gateway, services, databases, caches, queues.
4. **Deep dive**: data model, APIs, critical flows, bottlenecks.
5. **Trade-offs**: what you chose and why; failure handling; monitoring.

## 2. Building blocks

| Block | Purpose |
|---|---|
| Load balancer | distribute traffic, health checks |
| Stateless services | scale horizontally |
| Cache (Redis, CDN) | reduce latency & DB load |
| Database (SQL/NoSQL) | storage; replicas for reads; sharding for scale |
| Message queue/stream | async work, decoupling, smoothing spikes |
| Object storage (GCS/S3) | files, images |
| Search (Elasticsearch/OpenSearch) | full-text search |

## 3. Key concepts

- **Vertical vs horizontal scaling**.
- **Replication**: leader + read replicas (replication lag!).
- **Sharding/partitioning**: by key (customer id); hot partitions.
- **CAP theorem**: during a network partition choose Consistency or Availability. Payments → consistency; social feeds → availability.
- **Consistency models**: strong vs eventual.
- **Idempotency** and **exactly-once effects** for money.
- **Rate limiting**: token bucket.
- **Back-of-the-envelope**: 1M requests/day ≈ 12 req/s average; plan for peak ×10.

## 4. Practice 1: URL shortener

Requirements: create short link, redirect, 100M links, 10k redirects/s, links never change.
- API: `POST /links {url} → {code}`, `GET /{code} → 301/302`.
- Code generation: base62 of a unique id (sequence/Snowflake) → 7 chars = 3.5 trillion combinations.
- Storage: key-value (code → url); SQL is fine too with an index.
- Read-heavy → Redis cache + CDN for redirects.
- Analytics asynchronously via Kafka (click events).

## 5. Practice 2: payment-link system (like "Click to Birpay")

Requirements: merchants (500+) create payment links; customers pay by card without the merchant having a website; merchant sees payments in real time; no double charges.

```
Merchant app ─▶ API Gateway ─▶ Link Service (Postgres) ─▶ events ─▶ Notification Service
Customer browser ─▶ Pay page ─▶ Payment Service ─▶ Card processor (3-D Secure)
                                     │
                                     └─▶ outbox ─▶ Kafka ─▶ Merchant dashboard projection
```
Deep dive points:
- **Public code** (random, unguessable) instead of sequential ids.
- Link states: ACTIVE, PAID (single-use), EXPIRED, DISABLED.
- Payment flow with **idempotency key** per checkout attempt; status from processor via **webhooks** + reconciliation job for missing callbacks.
- Single-use link: atomic transition `ACTIVE → PAYING → PAID` with optimistic locking to prevent two parallel payments.
- Security: PCI DSS scope reduction (card data handled by processor's hosted fields), signed webhooks, rate limiting.
- Observability: payment success rate per merchant, latency to processor, alerts on drop.

## 6. Practice 3 (homework): QR payments for SMEs

Dynamic QR per purchase vs static QR per merchant; how the customer's banking app pays; how the merchant gets instant confirmation; refunds.

- How do you scale reads? Writes?
- How do you prevent double payments?
