> **Goal:** automate build, test and delivery with CI/CD pipelines in GitHub Actions.
> **Duration:** 120 min

## 1. CI and CD

- **Continuous Integration**: every push/PR is built and tested automatically; main is always green.
- **Continuous Delivery**: every green main build produces a deployable artifact (Docker image).
- **Continuous Deployment**: it is deployed automatically (often to staging, prod with approval).

Benefits: fast feedback, fewer "works on my machine" problems, small safe releases.

## 2. GitHub Actions basics

`.github/workflows/ci.yml`:
```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
          cache: gradle

      - name: Build and test
        run: ./gradlew spotlessCheck build jacocoTestReport

      - name: Upload test reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: reports
          path: build/reports
```
Testcontainers works on GitHub-hosted runners (Docker is available).

## 3. Building and pushing a Docker image

```yaml
  image:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:latest
```
Tag images with the **commit SHA**: you always know what is deployed.

## 4. Quality gates in the pipeline

| Stage | Tool |
|---|---|
| format | Spotless |
| unit + integration tests | Gradle + Testcontainers |
| coverage | JaCoCo (fail under threshold) |
| static analysis | SonarCloud |
| dependency vulnerabilities | Dependabot / OWASP check / Trivy |
| secrets | gitleaks |
| image scan | Trivy |

## 5. Deployment pipeline

```
PR → CI (build, test, scan) → merge → build image → deploy to staging → smoke tests → manual approval → deploy to prod
```
GitHub **environments** with protection rules and secrets per environment.

```yaml
  deploy-staging:
    needs: image
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh staging ${{ github.sha }}
      - run: ./smoke-test.sh https://staging.shop.az
```

## 6. Branching strategy

- **Trunk-based** (recommended): short-lived branches, PRs, main always deployable, feature flags for unfinished work.
- GitFlow: develop/release branches: heavier, used in some enterprises.
- Branch protection: required checks + review before merge.

## 7. Database migrations in CD

Flyway runs on startup → migrations must be **backward compatible** with the previous app version (expand & contract) because during rolling deploys old and new versions run together.
