## 1. Why cache?

Reading the product catalog from PostgreSQL 5,000 times per second is wasteful when it changes once an hour. A cache stores hot data in memory: microseconds instead of milliseconds.

## 2. Redis

In-memory data store: strings, hashes, lists, sets, sorted sets, TTL, pub/sub, streams, atomic operations.

```yaml
services:
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]
```
```bash
redis-cli SET rate:USD:AZN 1.70 EX 300
redis-cli GET rate:USD:AZN
redis-cli INCR login:attempts:ip:1.2.3.4
redis-cli ZADD leaderboard 1500 "leyla"
```

## 3. Spring Cache abstraction

```groovy
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.springframework.boot:spring-boot-starter-cache'
```
```java
@EnableCaching
@Configuration
class CacheConfig {
    @Bean
    RedisCacheConfiguration cacheConfiguration() {
        return RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(10))
                .serializeValuesWith(RedisSerializationContext.SerializationPair
                        .fromSerializer(new GenericJackson2JsonRedisSerializer()));
    }
}

@Service
class CatalogService {
    @Cacheable(cacheNames = "products", key = "#id")
    public ProductResponse get(Long id) { ... }               // DB only on cache miss

    @CachePut(cacheNames = "products", key = "#result.id()")
    public ProductResponse update(Long id, UpdateProductRequest r) { ... }

    @CacheEvict(cacheNames = "products", key = "#id")
    public void delete(Long id) { ... }

    @CacheEvict(cacheNames = "productLists", allEntries = true)
    public void importCatalog(...) { ... }
}
```
Cache **DTOs**, not JPA entities.

## 4. Caching strategies and problems

| Strategy | How |
|---|---|
| Cache-aside (lazy) | read cache → miss → DB → put (what `@Cacheable` does) |
| Write-through | write DB and cache together |
| TTL | entries expire automatically |

Problems:
- **Stale data**: choose TTL by business tolerance; evict on updates.
- **Cache stampede**: many requests miss at once → lock/`sync = true`, early refresh.
- **Inconsistency across instances**: use a shared cache (Redis), not local maps, or local cache with short TTL (Caffeine) for super-hot data.
- Don't cache personal/sensitive data without thought; never cache per-user data under shared keys.

> "There are only two hard things in computer science: cache invalidation and naming things."

## 5. Other Redis uses

- Rate limiting counters, login attempts.
- Distributed locks (carefully: Redisson / ShedLock for scheduled jobs).
- Session storage (Spring Session).
- Idempotency keys with TTL.

## 6. RabbitMQ vs Kafka

| | RabbitMQ | Kafka |
|---|---|---|
| Model | message broker, queues, routing (exchanges) | distributed log, topics/partitions |
| Message after consume | removed | retained (replayable) |
| Strength | task queues, complex routing, per-message ack, priorities, delays | high-throughput event streams, replay, ordering per key, stream processing |
| Typical use | "send this email", "generate this PDF" jobs | domain events, CDC, analytics pipelines, audit streams |

```java
@RabbitListener(queues = "pdf.generate")
void generate(GeneratePdfCommand cmd) { ... }
```
Both are fine; choose by need. Many companies use both.
