> **Goal:** keep services working when dependencies fail: circuit breakers, retries, bulkheads, rate limiters.
> **Duration:** 120 min

## 1. Cascading failures

Payments-provider becomes slow (10 s responses). Orders-service threads all wait → orders-service stops responding → gateway threads wait → **whole system down** because of one dependency.

## 2. Resilience4j

```groovy
implementation 'org.springframework.cloud:spring-cloud-starter-circuitbreaker-resilience4j'
implementation 'org.springframework.boot:spring-boot-starter-aop'
```

### Timeouts first
Every remote call has a timeout (HTTP client + `TimeLimiter`).

### Retry
```yaml
resilience4j.retry.instances.payments:
  max-attempts: 3
  wait-duration: 200ms
  enable-exponential-backoff: true
  exponential-backoff-multiplier: 2
  retry-exceptions: [java.io.IOException, org.springframework.web.client.ResourceAccessException]
```
Retry only **transient** errors and **idempotent** operations (or with idempotency keys).

### Circuit breaker
```
CLOSED ──(failure rate > 50%)──▶ OPEN ──(wait 30s)──▶ HALF_OPEN ──(test calls ok)──▶ CLOSED
                                  │ calls fail fast                    │ (fail) → OPEN
```
```yaml
resilience4j.circuitbreaker.instances.payments:
  sliding-window-size: 20
  failure-rate-threshold: 50
  slow-call-duration-threshold: 2s
  slow-call-rate-threshold: 50
  wait-duration-in-open-state: 30s
  permitted-number-of-calls-in-half-open-state: 3
```
```java
@CircuitBreaker(name = "payments", fallbackMethod = "paymentUnavailable")
@Retry(name = "payments")
public PaymentResult charge(PaymentRequest req) {
    return paymentClient.charge(req);
}

private PaymentResult paymentUnavailable(PaymentRequest req, Throwable t) {
    return PaymentResult.pending("Payment provider unavailable, will retry");   // degrade gracefully
}
```

### Bulkhead
Limit concurrent calls to one dependency so it can't consume all threads:
```yaml
resilience4j.bulkhead.instances.payments.max-concurrent-calls: 20
```

### Rate limiter
```yaml
resilience4j.ratelimiter.instances.sms:
  limit-for-period: 50
  limit-refresh-period: 1s
```

## 3. Fallback strategies

| Strategy | Example |
|---|---|
| cached value | last known exchange rate |
| default value | empty recommendations list |
| degrade feature | hide "offers" section |
| queue for later | accept order as PENDING, process payment async |
| fail fast with clear error | 503 + Retry-After |

Never fake success for money operations!

## 4. Observing resilience

Actuator: `/actuator/circuitbreakers`, metrics `resilience4j_circuitbreaker_state`. Alert when a breaker opens.

## 5. Hands-on

1. WireMock payment provider with configurable delay/failure.
2. Without resilience: show thread exhaustion under load (e.g. `hey`/`k6` load tool).
3. Add timeouts → retry → circuit breaker → bulkhead step by step; observe behaviour and metrics.
4. Fallback: order becomes `PAYMENT_PENDING`; a scheduled job retries later.
