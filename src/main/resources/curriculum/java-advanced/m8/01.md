> **Goal:** understand when and how to split a system into microservices.
> **Duration:** 120 min

## 1. Monolith vs microservices

| | Monolith | Microservices |
|---|---|---|
| Deployment | one unit | many independent services |
| Scaling | whole app | per service |
| Team autonomy | shared codebase | team per service |
| Data | one database | database per service |
| Complexity | in the code | in the **network & operations** |
| Failure | one bug can crash all | partial failures, but many more failure modes |
| Consistency | ACID transactions | eventual consistency, sagas |

> "Don't start with microservices." A **modular monolith** with clean boundaries is often the best start; extract services when there's a real reason (team scaling, independent scaling, different release cadence).

## 2. Domain-Driven Design essentials

- **Domain**: the business area (payments, onboarding, lending).
- **Bounded context**: a boundary where a model has one clear meaning. "Customer" in *Onboarding* (documents, KYC status) ≠ "Customer" in *Payments* (card, limits).
- **Ubiquitous language**: same words in code and in business conversations.
- **Aggregates**: consistency boundaries (an `Order` with its `OrderItems` changes together).

Service boundaries should follow **bounded contexts**, not technical layers ("user-service", "email-service" for everything is usually wrong).

## 3. Case study: ECOM onboarding migration (from real work)

A merchant onboarding flow lived inside a big monolithic business banking application. Problems: slow releases, risky deployments, one team blocking another.

Migration approach (strangler fig):
1. Identify the bounded context: **merchant onboarding** (application, documents, verification, contract, activation).
2. Build the new service next to the monolith with its own database.
3. Route new traffic to the new service via a gateway; keep the old path for existing flows.
4. Sync data with events during the transition.
5. Remove the old code when traffic is fully migrated.

Result: independent deployments, better scalability, much lower deployment downtime.

## 4. Communication styles

| Style | Example | Pros | Cons |
|---|---|---|---|
| Synchronous (REST/gRPC) | orders → inventory "reserve" | simple, immediate answer | coupling, cascading failures |
| Asynchronous (events/messages) | `OrderPlaced` → notifications, analytics | decoupled, resilient | eventual consistency, harder debugging |

Rule of thumb: queries & commands needing an immediate answer → sync; reactions to things that happened → async events.

## 5. Data ownership

- Each service owns its data; **no shared database** between services.
- Others get data via API or events (and keep local copies/projections if needed).

## 6. The fallacies of distributed computing

The network is reliable; latency is zero; bandwidth is infinite; the network is secure; topology doesn't change; there is one administrator; transport cost is zero; the network is homogeneous. **All false.** Design for failure: timeouts, retries, idempotency, circuit breakers (lesson 4).

## 7. Hands-on

Split the shop into services on paper:
1. Identify bounded contexts (catalog, ordering, payments, inventory, notifications, customers).
2. For each: responsibilities, data owned, APIs, events published/consumed.
3. Draw the context map and the "place order" flow (sync + async parts).
4. Decide: which parts would you keep as a modular monolith?
