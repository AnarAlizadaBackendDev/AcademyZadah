> **Goal:** design event-driven systems with the outbox pattern, sagas and idempotency.
> **Duration:** 120 min

## 1. Events vs commands

| | Command | Event |
|---|---|---|
| Meaning | "do this" | "this happened" |
| Name | `ReserveStock` | `StockReserved` |
| Receivers | one | zero or many |
| Can be rejected | yes | no (it's a fact) |

Event design: past tense, immutable, contains an `eventId`, `occurredAt`, aggregate id and enough data for consumers (or a reference).

## 2. The dual-write problem

```java
@Transactional
void placeOrder(...) {
    orders.save(order);                       // DB commit
    kafka.send("orders.placed", event);       // what if this fails? or DB rolls back after send?
}
```
DB and Kafka can't share a transaction → lost or phantom events.

## 3. Transactional outbox

```sql
CREATE TABLE outbox (
    id           UUID PRIMARY KEY,
    aggregate_id VARCHAR(64) NOT NULL,
    type         VARCHAR(100) NOT NULL,
    payload      JSONB NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);
```
```java
@Transactional
void placeOrder(...) {
    orders.save(order);
    outbox.save(OutboxEvent.of("OrderPlaced", order.getId(), payload));   // same DB transaction ✅
}

@Scheduled(fixedDelay = 500)
@Transactional
void relay() {
    List<OutboxEvent> batch = outbox.lockNextBatch(100);   // SELECT ... FOR UPDATE SKIP LOCKED
    for (OutboxEvent e : batch) {
        kafka.send(e.topic(), e.aggregateId(), e.payload()).join();
        e.markPublished();
    }
}
```
Production alternative: **Debezium** CDC reads the outbox table from the DB log and publishes to Kafka.
At-least-once → consumers idempotent.

## 4. Sagas: distributed transactions without 2PC

Place order across services: reserve stock (inventory) → charge payment (payments) → confirm order (orders). If payment fails → **compensate**: release stock, cancel order.

### Choreography (events)
```
Orders: OrderCreated ─▶ Inventory: StockReserved ─▶ Payments: PaymentCompleted ─▶ Orders: confirm
                                                   └▶ PaymentFailed ─▶ Inventory: release ─▶ Orders: cancel
```
+ simple, decoupled; − flow is hard to see as it grows.

### Orchestration (a coordinator)
```java
class PlaceOrderSaga {
    void start(Order o)            { send(new ReserveStock(o)); }
    void on(StockReserved e)       { send(new ChargePayment(e)); }
    void on(StockRejected e)       { cancel(e.orderId(), "out of stock"); }
    void on(PaymentCompleted e)    { confirm(e.orderId()); }
    void on(PaymentFailed e)       { send(new ReleaseStock(e)); cancel(e.orderId(), "payment failed"); }
}
```
+ explicit flow, easier monitoring; − central component. Saga state stored in DB. Tools: Temporal, Camunda, Axon.

## 5. Idempotency everywhere

- Producer retries → duplicate events.
- Consumers process with `processed_events(event_id)` table or natural idempotency (upserts, "if status == X").
- Commands carry an idempotency key.

## 6. Eventual consistency in UX

After placing an order the status is `PENDING` until payment completes. UI shows progress; API returns `202 Accepted` with a status URL; clients poll or receive a push/WebSocket.
