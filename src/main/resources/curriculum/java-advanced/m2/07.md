> **Goal:** make queries fast with indexes and read execution plans.
> **Duration:** 120 min

## 1. Why queries get slow

Without an index, `WHERE email = 'x'` reads **every row** (sequential scan). On 10 million rows that's seconds per query.

An **index** is a separate sorted structure (usually a **B-tree**) that points to rows, like a book's index.

## 2. Creating indexes

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);
CREATE UNIQUE INDEX uk_customers_email ON customers (email);   -- UNIQUE constraints create one
CREATE INDEX idx_orders_status_created ON orders (status, created_at);   -- composite
CREATE INDEX idx_customers_lower_email ON customers (lower(email));     -- expression
CREATE INDEX idx_orders_new ON orders (created_at) WHERE status = 'NEW'; -- partial
CREATE INDEX CONCURRENTLY idx_x ON big_table (col);                     -- no table lock (production)
```
Primary keys are indexed automatically. **Foreign keys are NOT**: index them yourself.

## 3. EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10;
```
```
Limit  (cost=0.43..12.1 rows=10) (actual time=0.03..0.05 rows=10 loops=1)
  ->  Index Scan Backward using idx_orders_customer_created on orders ...
Planning Time: 0.1 ms
Execution Time: 0.08 ms
```

| Node | Meaning |
|---|---|
| Seq Scan | reads whole table (bad on big tables for selective filters) |
| Index Scan | uses index, then reads rows |
| Index Only Scan | all needed data in the index (best) |
| Bitmap Heap Scan | many matches via index |
| Nested Loop / Hash Join / Merge Join | join strategies |

Compare `rows` (estimated) with `actual rows`; big differences → run `ANALYZE table;` to update statistics.

## 4. Composite index column order

Index `(status, created_at)` helps:
- `WHERE status = 'NEW'` ✅
- `WHERE status = 'NEW' AND created_at > ...` ✅
- `WHERE status = 'NEW' ORDER BY created_at` ✅
- `WHERE created_at > ...` alone ❌ (leftmost prefix rule)

Rule: equality columns first, then range/sort columns.

## 5. When indexes don't help

- Low selectivity (`gender`, boolean on 50/50 data).
- Functions on the column: `WHERE lower(email) = ...` needs an expression index.
- `LIKE '%text'` (leading wildcard): B-tree can't help (use trigram `pg_trgm` index).
- Implicit casts, `OR` across different columns.
- Small tables (seq scan is faster).

## 6. Cost of indexes

- Every INSERT/UPDATE/DELETE must update all indexes → slower writes.
- Disk space.
- Don't index everything: index for your **real queries**.

Find unused indexes:
```sql
SELECT relname, indexrelname, idx_scan FROM pg_stat_user_indexes ORDER BY idx_scan;
```
Find slow queries: enable `pg_stat_statements`.

## 7. Other performance tips

- Select only needed columns (not `SELECT *`).
- Pagination with **keyset** for deep pages:
```sql
SELECT * FROM orders WHERE id < :lastSeenId ORDER BY id DESC LIMIT 20;   -- instead of OFFSET 100000
```
- Avoid N+1 queries from the application (month 3!).
- Batch inserts.

## 8. Hands-on

```sql
CREATE TABLE payments_big AS
SELECT g AS id,
       (random() * 100000)::int AS customer_id,
       (ARRAY['NEW','PAID','FAILED'])[1 + (random() * 2)::int] AS status,
       now() - (random() * interval '365 days') AS created_at,
       round((random() * 1000)::numeric, 2) AS amount
FROM generate_series(1, 2000000) g;
ANALYZE payments_big;
```
1. Time `WHERE customer_id = 123` before and after an index.
2. Optimise "last 20 PAID payments of a customer".
3. Show a case where the index is **not** used and explain why.
4. Compare OFFSET pagination at page 50,000 vs keyset pagination.
