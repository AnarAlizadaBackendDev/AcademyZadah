## 1. Transactions

A transfer = withdraw from A **and** deposit to B. If the system crashes between them, money disappears. A **transaction** makes several statements **all-or-nothing**.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
INSERT INTO transfers (from_id, to_id, amount) VALUES (1, 2, 100);
COMMIT;        -- or ROLLBACK; to undo everything
```

## 2. ACID

| Letter | Meaning |
|---|---|
| **A**tomicity | all or nothing |
| **C**onsistency | constraints always hold |
| **I**solation | concurrent transactions don't see each other's half-done work |
| **D**urability | committed data survives crashes (WAL) |

## 3. Concurrency anomalies

| Anomaly | What happens |
|---|---|
| Dirty read | reading uncommitted changes of another transaction |
| Non-repeatable read | same row read twice gives different values |
| Phantom read | same query returns new rows |
| Lost update | two transactions read-modify-write; one overwrites the other |

## 4. Isolation levels

| Level | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| Read Uncommitted* | possible | possible | possible |
| **Read Committed** (PG default) | ❌ | possible | possible |
| Repeatable Read | ❌ | ❌ | ❌ in PG |
| Serializable | ❌ | ❌ | ❌ |

*PostgreSQL treats it as Read Committed.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
...
COMMIT;   -- may fail with "could not serialize access": retry the transaction
```

## 5. Locking

### Pessimistic: lock the row
```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- others wait
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```
`FOR UPDATE SKIP LOCKED`: great for job queues (each worker takes different rows).
`FOR UPDATE NOWAIT`: fail immediately if locked.

### Optimistic: version column
```sql
UPDATE accounts SET balance = 400, version = version + 1
WHERE id = 1 AND version = 7;     -- 0 rows updated → someone changed it → retry
```
(JPA `@Version` does this for you; month 3.)

### Atomic update (simplest when possible)
```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100;
-- 1 row → success, 0 rows → insufficient funds
```

## 6. Deadlocks in the database

Two transactions locking rows in opposite order → PostgreSQL detects and aborts one (`deadlock detected`). Fix: lock in a **consistent order** (e.g. by account id), keep transactions short.
