> **Goal:** design good database schemas with ER diagrams and normalization.
> **Duration:** 120 min

## 1. From requirements to ERD

1. Find **entities** (nouns): Customer, Product, Order, Payment.
2. Find **attributes**: Customer(name, email, phone).
3. Find **relationships** and **cardinality**: Customer 1—N Order; Order N—M Product (via OrderItem).
4. Choose keys.

### ERD notation (crow's foot)
```
CUSTOMER ||──o{ ORDER ||──|{ ORDER_ITEM }o──|| PRODUCT
                 │
                 ||──o| PAYMENT
```
`||` exactly one, `o{` zero or many, `|{` one or many, `o|` zero or one.

Tools: dbdiagram.io, draw.io, DBeaver ER view.

```
// dbdiagram.io syntax
Table customers { id bigint [pk] name varchar email varchar [unique] }
Table orders { id bigint [pk] customer_id bigint [ref: > customers.id] status varchar created_at timestamptz }
```

## 2. Normalization

Goal: **no redundancy**, no update anomalies.

### 1NF: atomic values, no repeating groups
❌ `phones = '050..., 055...'` → ✅ separate `customer_phones` table.

### 2NF: every non-key column depends on the **whole** key
In `order_items(order_id, product_id, quantity, product_name)`, `product_name` depends only on `product_id` → move it to `products`.

### 3NF: no column depends on another non-key column
`customers(id, city_id, city_name)`: `city_name` depends on `city_id` → `cities` table.

> "Every non-key attribute must depend on the key, the whole key, and nothing but the key."

## 3. Anomalies without normalization

| Anomaly | Example |
|---|---|
| update | product name stored in 1000 order rows; renaming requires 1000 updates |
| insert | can't add a product until someone orders it |
| delete | deleting the last order removes the product info |

## 4. When to denormalize

- **Historical facts**: store `unit_price` in `order_items` (price at purchase time, not the current price!). This is not a normalization mistake: it's a different fact.
- Read-heavy reports: summary tables, materialized views.
- Caching counts (`comments_count`) with care.

## 5. Practical design rules

- Surrogate keys (`id BIGINT`) + natural unique constraints (`email UNIQUE`, `iban UNIQUE`).
- Money: `NUMERIC(19,4)` + currency column.
- Status columns with CHECK or lookup tables.
- `created_at`, `updated_at` on every business table.
- Never store derived data you can't keep consistent (e.g. account balance **and** transactions: keep balance updated in the same transaction, or compute it).
- Avoid EAV (entity-attribute-value) designs; use JSONB for truly flexible attributes.

## 6. Case study: payment-link system (like Click to Birpay)

Requirements: merchants create payment links with an amount and description; customers open the link and pay by card; a link can be single-use or multi-use; merchants see payments.

```
merchants(id, name, tax_id UNIQUE, status, created_at)
payment_links(id, merchant_id FK, public_code UNIQUE, amount NUMERIC NULL, currency,
              description, single_use BOOL, expires_at, status, created_at)
payments(id, link_id FK, amount, currency, card_mask, status, provider_ref UNIQUE, created_at)
```
Discuss: why `public_code` instead of exposing `id`? (security: ids are guessable) Why `amount NULL`? (customer enters the amount for donation-type links)
