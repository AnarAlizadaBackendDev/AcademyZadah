> **Goal:** understand Inversion of Control and Dependency Injection: the foundation of Spring.
> **Duration:** 120 min

## 1. Tight coupling problem

```java
public class OrderService {
    private final PaymentGateway gateway = new KapitalCardGateway();   // hard-coded
    private final SmsNotifier notifier = new SmsNotifier();

    public void placeOrder(Order order) { ... }
}
```
Problems:
- To switch to another gateway you edit `OrderService`.
- You can't test without real SMS/payment calls.
- Every class decides how to build its dependencies.

## 2. Dependency Injection by hand

```java
public class OrderService {
    private final PaymentGateway gateway;
    private final Notifier notifier;

    public OrderService(PaymentGateway gateway, Notifier notifier) {   // dependencies come from outside
        this.gateway = gateway;
        this.notifier = notifier;
    }
}

// composition root (main)
PaymentGateway gateway = new KapitalCardGateway(config);
Notifier notifier = new SmsNotifier(smsClient);
OrderService orders = new OrderService(gateway, notifier);
```
In tests: `new OrderService(new FakeGateway(), new InMemoryNotifier())`.

## 3. Inversion of Control

Instead of *your code* creating objects, a **container** creates and wires them. You describe *what* you need; the framework controls *when and how*. That container is the Spring **ApplicationContext**.

## 4. Spring does the wiring

```java
@Component
public class SmsNotifier implements Notifier { ... }

@Component
public class KapitalCardGateway implements PaymentGateway { ... }

@Service
public class OrderService {
    private final PaymentGateway gateway;
    private final Notifier notifier;

    public OrderService(PaymentGateway gateway, Notifier notifier) {   // constructor injection
        this.gateway = gateway;
        this.notifier = notifier;
    }
}

@SpringBootApplication
public class ShopApplication {
    public static void main(String[] args) {
        ApplicationContext ctx = SpringApplication.run(ShopApplication.class, args);
        OrderService service = ctx.getBean(OrderService.class);
    }
}
```
At startup Spring:
1. **scans** packages for `@Component`, `@Service`, `@Repository`, `@Controller`, `@Configuration`;
2. creates **beans** (objects managed by Spring);
3. **injects** dependencies via constructors.

## 5. Injection types

| Type | Example | Verdict |
|---|---|---|
| **Constructor** | `public OrderService(PaymentGateway g)` | ✅ recommended: immutable, testable, required deps clear |
| Setter | `@Autowired void setX(X x)` | optional deps only |
| Field | `@Autowired private X x;` | ❌ hides deps, hard to test |

With one constructor, `@Autowired` is not needed.

## 6. Multiple implementations

```java
@Component("cardGateway") class CardGateway implements PaymentGateway { }
@Component("qrGateway")   class QrGateway implements PaymentGateway { }

public OrderService(@Qualifier("qrGateway") PaymentGateway gateway) { ... }

@Primary @Component class DefaultGateway implements PaymentGateway { }   // default choice

public PaymentRouter(List<PaymentGateway> gateways) { ... }            // inject ALL
public PaymentRouter(Map<String, PaymentGateway> byName) { ... }       // bean name → bean
```

## 7. Hands-on

1. Build the `OrderService` example without Spring (manual DI) and test it with fakes.
2. Create a Spring Boot project (Initializr: no extra deps) and convert it to beans.
3. Add two `Notifier` implementations; use `@Primary`, then `@Qualifier`, then inject a `List<Notifier>`.
4. Print all bean names from the context: `ctx.getBeanDefinitionNames()`.

## 8. Interview corner

- What is IoC? What is DI?
- Why is constructor injection preferred?
- What happens when two beans implement the same interface?
- What is the ApplicationContext?
