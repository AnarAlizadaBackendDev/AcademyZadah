> **Goal:** build a testing strategy: what to test, at which level, and how.
> **Duration:** 120 min

## 1. Why a strategy?

Teams without a strategy either have no tests (fear of change) or slow, flaky tests nobody trusts. Good tests let you deploy **daily with confidence**.

## 2. The test pyramid

```
            ▲  few, slow, expensive
           ╱ ╲      E2E / UI tests
          ╱───╲
         ╱     ╲    Integration tests (DB, HTTP, Kafka)
        ╱───────╲
       ╱         ╲  Unit tests (domain, services with mocks)
      ╱───────────╲ many, fast, cheap
```
Modern variant for microservices ("testing honeycomb"): more weight on **integration tests** with real dependencies (Testcontainers), because most bugs are at the boundaries.

| Level | Tests | Speed | Example |
|---|---|---|---|
| Unit | one class/function | ms | `Order.addItem` calculates total |
| Slice | one layer with Spring | 100s ms | `@WebMvcTest` controller, `@DataJpaTest` repository |
| Integration | app + real DB/broker | seconds | place order end-to-end with PostgreSQL |
| Contract | API compatibility between services | seconds | consumer expectations |
| E2E | whole system via UI/API | minutes | smoke test after deploy |

## 3. What to test

✅ Business rules and edge cases (money, limits, state transitions).
✅ Queries you wrote (they break silently).
✅ Security rules.
✅ Error handling and mapping.
✅ Integration with external systems (with stubs).
❌ Getters/setters, framework code, trivial mappings.

Coverage is a **signal**, not a goal: 80% meaningful > 100% of assertions on getters.

## 4. Good tests are FIRST

- **F**ast
- **I**ndependent (no order, no shared state)
- **R**epeatable (no dependency on time/network/random without control)
- **S**elf-validating (pass/fail, no manual checks)
- **T**imely (written with the code)

## 5. Naming and structure

```java
@Test
void placeOrder_failsWhenStockIsInsufficient() { ... }

@Test
@DisplayName("order total includes VAT and discounts")
void totalIncludesVatAndDiscounts() { ... }
```
Given/When/Then (Arrange/Act/Assert), one behaviour per test.

## 6. Test doubles

| Double | What it is |
|---|---|
| Dummy | passed but not used |
| Stub | returns canned answers |
| Fake | working lightweight implementation (in-memory repo) |
| Mock | verifies interactions |
| Spy | real object with recorded calls |

Prefer **fakes and real objects** for domain logic; mocks for boundaries (payment provider, email).

## 7. Testability by design

- Constructor injection → easy to pass doubles.
- Inject `Clock` instead of `Instant.now()`.
- Pure domain logic without Spring.
- Small classes with one responsibility.

## 8. Hands-on

1. Classify your shop's existing tests by level; draw your current "pyramid".
2. Write a test plan: for each feature list unit/slice/integration tests needed.
3. Refactor one time-dependent method to use `Clock`; test it with `Clock.fixed(...)`.

## 9. Interview corner

- Explain the test pyramid.
- Mock vs stub vs fake?
- Is 100% coverage a good goal?

## 10. Homework

`TESTING.md` for the shop: strategy, levels, tools, what each test type covers; target numbers per level.
