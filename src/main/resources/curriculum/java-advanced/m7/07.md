> **Goal:** measure and improve code quality with coverage, static analysis and code reviews.
> **Duration:** 120 min

## 1. Coverage with JaCoCo

```groovy
plugins { id 'jacoco' }

jacocoTestReport {
    dependsOn test
    reports { html.required = true; xml.required = true }
}

jacocoTestCoverageVerification {
    violationRules {
        rule { limit { minimum = 0.80 } }
    }
}
check.dependsOn jacocoTestCoverageVerification
```
`./gradlew test jacocoTestReport` → `build/reports/jacoco/test/html/index.html`

- **Line** coverage: lines executed.
- **Branch** coverage: both sides of `if`s: more meaningful.
- Exclude generated code (MapStruct, configs, DTOs) from metrics.

Coverage shows what is **not** tested; it doesn't prove tests are good. **Mutation testing** (PIT) does: it changes your code (e.g. `>` to `>=`) and checks if tests fail.
```groovy
plugins { id 'info.solidsoft.pitest' version '1.15.0' }
```

## 2. Static analysis

| Tool | Finds |
|---|---|
| **SonarQube / SonarCloud** | bugs, code smells, security hotspots, duplication, coverage dashboard |
| SpotBugs | bug patterns in bytecode |
| PMD / Checkstyle | style and rule violations |
| Error Prone | compile-time bug detection |
| IntelliJ inspections | everything above, live |

SonarQube locally:
```bash
docker run -d --name sonar -p 9000:9000 sonarqube:community
./gradlew sonar -Dsonar.host.url=http://localhost:9000 -Dsonar.token=...
```
**Quality gate**: e.g. no new bugs, coverage on new code ≥ 80%, no new critical issues → blocks merge in CI.

## 3. Formatting

Spotless + google-java-format or Palantir: formatting is automated, never discussed in reviews.
```groovy
plugins { id 'com.diffplug.spotless' version '6.25.0' }
spotless { java { palantirJavaFormat() } }
```

## 4. Code review

What reviewers check:
1. **Correctness**: does it do what the ticket says? edge cases?
2. **Design**: right place, right abstraction, no duplication.
3. **Readability**: names, size, comments explain why.
4. **Tests**: meaningful, cover new behaviour.
5. **Security & performance**: N+1, missing auth checks, secrets, unbounded queries.
6. **Operability**: logs, metrics, migrations safe for production.

How to give feedback:
- Comment on code, not the person.
- Explain **why**; suggest alternatives.
- Mark severity: `blocker:`, `suggestion:`, `nit:`.
- Approve when good enough, not perfect.

Small PRs (< 400 lines) get better reviews.

## 5. Refactoring safely

With good tests:
1. Make the change easy (refactor), then make the easy change.
2. Small steps, run tests after each.
3. IntelliJ automated refactorings.

Typical refactorings: extract method/class, replace conditional with polymorphism, introduce parameter object, move method to the class that owns the data.

## 6. Hands-on

1. JaCoCo report; find untested branches; add tests.
2. Run PIT on the domain package; kill surviving mutants.
3. SonarQube scan; fix bugs and code smells.
4. Peer code review of another student's PR using the checklist.

## 7. Interview corner

- What is a quality gate?

## 8. Homework

Reach ≥ 80% branch coverage on business logic, clean Sonar quality gate, Spotless formatting enforced in the build.
