> **Goal:** create domain-specific exceptions and follow error-handling best practices.
> **Duration:** 90 min

## 1. Why custom exceptions?

`IllegalArgumentException("not enough money")` works, but the caller can't easily distinguish *why* it failed. Custom exceptions express **business errors** clearly:

```java
public class InsufficientFundsException extends RuntimeException {
    private final double requested;
    private final double available;

    public InsufficientFundsException(double requested, double available) {
        super(String.format("Requested %.2f but only %.2f available", requested, available));
        this.requested = requested;
        this.available = available;
    }

    public double getRequested() { return requested; }
    public double getAvailable() { return available; }
}
```

## 2. Checked or unchecked?

Modern practice (and Spring): **unchecked** (`extends RuntimeException`) for business errors. Checked exceptions make code noisy and leak through every layer.

## 3. Throwing and handling

```java
public class BankAccount {
    public void withdraw(double amount) {
        if (amount > balance) {
            throw new InsufficientFundsException(amount, balance);
        }
        balance -= amount;
    }
}
```
```java
try {
    account.withdraw(500);
} catch (InsufficientFundsException e) {
    System.out.println("❌ " + e.getMessage());
    System.out.println("You can withdraw at most " + e.getAvailable());
}
```

## 4. A small hierarchy

```java
public class BankException extends RuntimeException {
    public BankException(String message) { super(message); }
    public BankException(String message, Throwable cause) { super(message, cause); }
}
public class AccountNotFoundException extends BankException { ... }
public class InsufficientFundsException extends BankException { ... }
public class AccountBlockedException extends BankException { ... }
```
The UI can `catch (BankException e)` for all of them, or catch specific ones.

## 5. Exception chaining

Wrap low-level exceptions without losing the original cause:
```java
try {
    String json = Files.readString(path);
} catch (IOException e) {
    throw new BankException("Cannot load accounts from " + path, e);   // keep the cause!
}
```
The stack trace will show `Caused by: java.nio.file.NoSuchFileException...`.

## 6. Where to catch?

- **Throw** where the problem is detected (deep in the model/service).
- **Catch** where you can do something useful (UI layer: show a message; or retry).
- Don't catch just to re-throw the same thing.

```
UI (catch & show message)
  ↓ calls
Service (business rules, throws BankException)
  ↓ calls
Model / Repository (throws)
```

## 7. Best practices checklist

- ✅ Specific exception types with clear messages including the **values**.
- ✅ Fail fast: validate arguments at the start of methods.
- ✅ Keep the cause when wrapping.
- ❌ `catch (Exception e) { e.printStackTrace(); }` everywhere.
- ❌ Returning `null` or `-1` to signal errors.
- ❌ Exceptions for normal situations (e.g. "user not found" during a search is often a normal empty result).

## 8. Step by step: transfer service

```java
public class TransferService {
    private final AccountRepository accounts;

    public TransferService(AccountRepository accounts) { this.accounts = accounts; }

    public void transfer(String fromIban, String toIban, double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (fromIban.equals(toIban)) throw new BankException("Cannot transfer to the same account");

        BankAccount from = accounts.find(fromIban);   // throws AccountNotFoundException
        BankAccount to = accounts.find(toIban);

        from.withdraw(amount);                        // may throw InsufficientFundsException
        to.deposit(amount);
    }
}
```

## 11. Self-check

1. Why do Spring projects usually use unchecked exceptions?
2. What is exception chaining?
3. Where is the best place to catch an exception?

<details><summary>Answers</summary>

1. They don't force every layer to declare/catch them, keeping code clean; a central handler deals with them.
2. Wrapping a low-level exception in a higher-level one while keeping the original as the cause.
3. Where you can handle it meaningfully: usually the outer layer (UI/controller) or where a retry is possible.

</details>
