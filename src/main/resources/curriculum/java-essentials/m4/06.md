> **Goal:** write automated unit tests with JUnit 5 and get started with TDD.
> **Duration:** 90 min

## 1. Why test?

- Catch bugs **before** users do.
- Change code without fear (refactoring).
- Tests are **documentation**: they show how code is supposed to work.
- Every serious company requires tests in pull requests.

## 2. Setup (Gradle)

```groovy
dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter:5.11.0'
}
test {
    useJUnitPlatform()
}
```
Tests live in `src/test/java`, mirroring the package of the tested class.

## 3. First test

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class BankAccountTest {

    @Test
    void depositIncreasesBalance() {
        // Arrange
        BankAccount account = new BankAccount("Leyla", "AZ01");

        // Act
        account.deposit(100);

        // Assert
        assertEquals(100, account.getBalance(), 0.0001);
    }
}
```
Run: green ▶ in IntelliJ or `./gradlew test`.

## 4. Assertions

```java
assertEquals(expected, actual);
assertEquals(0.3, 0.1 + 0.2, 1e-9);           // doubles need a delta
assertTrue(account.isActive());
assertFalse(list.isEmpty());
assertNull(x); assertNotNull(y);
assertIterableEquals(List.of(1, 2), result);
assertThrows(InsufficientFundsException.class, () -> account.withdraw(1_000));
assertAll(
    () -> assertEquals("Leyla", acc.getOwner()),
    () -> assertEquals(0, acc.getBalance())
);
```

## 5. Structure and lifecycle

```java
class TodoListTest {
    private TodoList todo;

    @BeforeEach
    void setUp() {
        todo = new TodoList();          // fresh object for every test
    }

    @Test
    @DisplayName("completed tasks are not pending")
    void completedTaskIsNotPending() {
        Task t = todo.add("Learn JUnit");
        todo.complete(t.id());
        assertTrue(todo.pending().isEmpty());
    }
}
```

Good test names describe **behaviour**: `withdrawFailsWhenBalanceIsTooLow`.

## 6. What to test

- The **happy path** (normal case).
- **Edge cases**: 0, negative, empty list, max values, null.
- **Error cases**: the right exception is thrown.

```java
@Test
void withdrawFailsWhenAmountIsNegative() {
    var acc = new BankAccount("Leyla", "AZ01");
    var ex = assertThrows(IllegalArgumentException.class, () -> acc.withdraw(-5));
    assertTrue(ex.getMessage().contains("positive"));
}
```

## 7. Test-Driven Development (TDD)

1. 🔴 **Red**: write a failing test for the next small behaviour.
2. 🟢 **Green**: write the simplest code to pass.
3. 🔵 **Refactor**: clean up, tests stay green.

### TDD kata: password validator
Rules: ≥ 8 chars, at least one digit, one uppercase letter.
```java
@Test void shortPasswordIsInvalid() { assertFalse(PasswordValidator.isValid("Ab1")); }
@Test void passwordWithoutDigitIsInvalid() { assertFalse(PasswordValidator.isValid("Abcdefgh")); }
@Test void passwordWithoutUppercaseIsInvalid() { assertFalse(PasswordValidator.isValid("abcdefg1")); }
@Test void validPassword() { assertTrue(PasswordValidator.isValid("Secret123")); }
```
Write them one by one, each time making it pass.

## 8. Common mistakes

- ❌ Tests that depend on each other or on execution order.
- ❌ Testing private methods directly: test through the public API.
- ❌ One giant test checking 20 things.
- ❌ `assertEquals(actual, expected)`: wrong order gives confusing messages.
- ❌ Comparing doubles without delta.
