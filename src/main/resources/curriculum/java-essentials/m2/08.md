## 2. Designing before coding

Steps professionals follow:
1. Read requirements, underline **nouns** → candidate classes; **verbs** → methods.
2. Draw a simple class diagram.
3. Decide responsibilities: *who knows what? who does what?*
4. Code the model, then the service, then the UI (menu).

### Simple UML notation
```
┌──────────────────┐        ┌──────────────────┐
│ Book             │        │ Member           │
├──────────────────┤        ├──────────────────┤
│ - isbn: String   │        │ - id: int        │
│ - title: String  │        │ - name: String   │
│ - available: bool│        │ - borrowed: Book[]│
├──────────────────┤        ├──────────────────┤
│ + borrow()       │        │ + canBorrow()    │

        ▲

└──────────────────┘
```
`-` private, `+` public.

## 3. 🏁 Month 2 Project: Library Management System

### Requirements
1. Items: `Book` and `Magazine` (both are `LibraryItem`), each with id, title, year. Books have an author and ISBN; magazines have an issue number.
2. `Member` with id, name, type (`STUDENT` max 3 items, `REGULAR` max 5): use an **enum** with the limit inside.
3. A member can **borrow** an available item and **return** it. Borrowing fails if the item is taken or the limit is reached (print the reason).
4. Each borrowing creates a `Loan` **record** (itemId, memberId, date).
5. Menu:
```
1) Add book       2) Add magazine     3) Add member
4) Borrow item    5) Return item      6) List available items
7) List member's items                0) Exit
```
6. Search items by title (case-insensitive, partial match).

### Suggested design
```java
public abstract class LibraryItem { id, title, year, available; abstract String details(); }
public class Book extends LibraryItem { author, isbn }
public class Magazine extends LibraryItem { issue }
public enum MemberType { STUDENT(3), REGULAR(5); ... }
public class Member { id, name, type, LibraryItem[] items, int count }
public record Loan(int itemId, int memberId, java.time.LocalDate date) { }
public class Library { items, members, loans; add..., borrow(...), giveBack(...), search(...) }
public class LibraryApp { main + menu }
```
(We use arrays with a counter this month; in month 3 you will refactor to `List` and `Map`.)

### Rules that must hold (invariants)
- An item cannot be borrowed twice.
- A member never exceeds the limit.
- Returning an item not borrowed by that member is rejected.

### Evaluation checklist
- [ ] Abstract class + 2 subclasses with overridden `details()`
- [ ] Enum with a field, record for loans
- [ ] All fields private, validation in constructors/methods
- [ ] `Library` contains the logic; `LibraryApp` only handles input/output
- [ ] Meaningful messages for every failure
- [ ] Clean packages: `model`, `service`, `app`

## 4. Self-check

1. Why should `LibraryApp` not contain business rules?
2. Where should the "max items" rule live?
3. Why is `Loan` a record but `Member` a class?

<details><summary>Answers</summary>

1. Separation of concerns: UI can change (console → web) without touching the rules.
2. In the `MemberType` enum / `Member.canBorrow()`: the object that owns the data owns the rule.
3. A loan is an immutable fact; a member's state (borrowed items) changes.

</details>

## Teaching tips
- Review designs **before** students code too much; fixing design early saves hours.
- Typical problem: all logic in `main`. Ask "if we build a web version, which code do we keep?".
