> **Goal:** protect object state with encapsulation and design safe classes.
> **Duration:** 90 min

## 1. The problem

```java
BankAccount acc = new BankAccount("Leyla", "AZ1");
acc.balance = -1_000_000;   // anyone can break the rules!
```
A class must **protect its data** and allow changes only through methods that check the rules. This is **encapsulation**.

## 2. Access modifiers

| Modifier | Visible in |
|---|---|
| `private` | the same class only |
| *(none)* package-private | the same package |
| `protected` | same package + subclasses |
| `public` | everywhere |

Rule of thumb: **fields `private`, methods `public` only if needed by others.**

## 3. Encapsulated BankAccount

```java
public class BankAccount {
    private final String iban;      // never changes
    private final String owner;
    private double balance;

    public BankAccount(String owner, String iban) {
        if (owner == null || owner.isBlank()) {
            throw new IllegalArgumentException("Owner is required");
        }
        this.owner = owner;
        this.iban = iban;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        balance += amount;
    }

    public boolean withdraw(double amount) {
        if (amount <= 0 || amount > balance) {
            return false;
        }
        balance -= amount;
        return true;
    }

    public double getBalance() { return balance; }
    public String getIban() { return iban; }
    public String getOwner() { return owner; }
}
```

- No `setBalance()`: the balance changes only through `deposit` and `withdraw`.
- `final` fields are set once in the constructor.
- `throw new IllegalArgumentException(...)` stops invalid input (exceptions in month 3).

## 4. Getters and setters

```java
public String getName() { return name; }
public void setName(String name) {
    if (name == null || name.isBlank()) throw new IllegalArgumentException("Name required");
    this.name = name.trim();
}
public boolean isActive() { return active; }   // boolean getter starts with "is"
```
Do **not** generate setters for everything automatically. Ask: *should this be changeable from outside?*

## 5. Immutable objects

An immutable object never changes after creation: all fields `private final`, no setters.
```java
public final class Money {
    private final double amount;
    private final String currency;

    public Money(double amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public Money add(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("Currency mismatch");
        return new Money(amount + other.amount, currency);   // returns a NEW object
    }

    public double getAmount() { return amount; }
    public String getCurrency() { return currency; }
}
```
Immutable objects are simple, thread-safe and safe to share. `String` is immutable for the same reasons.

## 6. `toString()` for readable output

```java
@Override
public String toString() {
    return "BankAccount{iban='" + iban + "', owner='" + owner + "', balance=" + balance + "}";
}
```
Now `System.out.println(acc)` prints something useful. (IntelliJ: Alt+Insert → toString.)

## 7. Common mistakes

- ❌ Public fields.
- ❌ Setters without validation.
- ❌ Getters returning internal mutable arrays/lists. Return a copy.
- ❌ Generating getters/setters for everything "just in case".

## 8. Exercises

1. Encapsulate `Student`: name required, scores 0–100 only, `addScore(int)`, `getAverage()`.
2. Create an immutable `Point(x, y)` with `moveBy(dx, dy)` returning a new point.
3. Add a transaction counter to `BankAccount` that can be read but not set.

## 9. Homework

`CreditCard` class: number (only last 4 digits visible through `getMaskedNumber()`), limit, debt. Methods: `pay(amount)` (fails if over limit), `repay(amount)`, `getAvailableLimit()`. Add `toString()` that never shows the full number.

## 10. Self-check

1. Why should fields be private?
2. Why is there no `setBalance` method?
3. What makes a class immutable?

<details><summary>Answers</summary>

1. So the object controls its own state and keeps its rules (invariants).
2. Balance must change only via operations that check the rules (deposit/withdraw).
3. Private final fields, no setters, methods return new objects instead of modifying state (and the class is final).

</details>
